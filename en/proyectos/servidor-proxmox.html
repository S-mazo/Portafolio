Overview

A lecturer found an unused Dell Precision 7820 workstation sitting at the university and claimed it. He asked me to manage it: turn it into a real server, with separated services and secure remote access.

The answer was Proxmox VE 9.2: a bare-metal hypervisor now running virtual machines for a research seedbed, an institutional community-service platform, a student's web project and an educational game server hosting service. All on a university network where exposing the institutional IP or opening ports is not an option: every service is published through tunnels and a mesh VPN.

It's a recent project — it started last month — and is in active growth: the hardware still has plenty of spare capacity (including an unassigned 48 GB GPU) and the decision of which new services to deploy is made on the fly. What already runs, runs in production with real users.

What I built

Proxmox VE hypervisor

Proxmox VE 9.2 installed on Debian Trixie: migration of repositories from enterprise to no-subscription (401 and Deb822 format errors), cleanup of inherited Intel IMSM RAID metadata (md127, wipefs) and ZFS pools built from scratch. A library of 6 ISOs ready to provision VMs.

Game servers (Pterodactyl)

A low-level tuned KVM VM —CPU in host mode, fixed RAM with no ballooning, VirtIO SCSI with iothread and discard on ZFS, multiqueue networking— running the Pterodactyl Panel + Wings stack on LEMP. First deployment: an educational Minecraft server, with Docker per server and game traffic published securely.

Infrastructure for others

VMs provisioned for others: the lecturer's (4 sites —research seedbed, vice-rectorate community-service platform and two more projects— on nginx + 3 Python/Gunicorn apps) and a student's behind openresty. Each with its own isolated VM and its own egress tunnel.

Network without a public IP

Secure exposure under university restrictions: Cloudflare Tunnel (outbound connections, TLS at the edge) for web traffic, Tailscale as the management mesh VPN with 7 devices and a dedicated TCP/UDP tunnel for game traffic, routed via DNS SRV.

Security and segregation

Permission model with Proxmox ACLs: a second administrator with the Administrator role over the whole datacenter except the production game VM, locked with NoAccess. SSH by keys only, and remote management only over VPN.

Test environments

A Windows VM with UEFI + emulated TPM 2.0 + Secure Boot for a testing lab, isolated from production services.

Notable decisions: host-mode CPU and fixed RAM on the game VM for predictable performance, at the cost of losing hypervisor metrics; iothread + discard to avoid double caching between ZFS and the guest; custom systemd services and cron for the panel scheduler and queues; and manual repair of the Wings configuration when the panel generated SSL enabled behind a proxy that already terminated TLS.

Engineering and operations

  • Rescued the hardware: both 4 TB HDDs were trapped in an inactive Intel IMSM RAID. I diagnosed the metadata, stopped the array and wiped the signatures with wipefs — without touching the install USB, the only thing that had to survive.
  • Server up in 4 hours: Proxmox installed, repositories fixed (enterprise → no-subscription, 401 and format errors), SSH and Tailscale working the same day. The full environment took ~1 month of intermittent work.
  • Iterated to the right VM: the current production VM is its third iteration (create → destroy → recreate), tuning resources each cycle. 7 VMs created in total, 4 active.
  • Diagnosed performance with data: fixed a CPU pinning configuration that confused "number of cores" with "core IDs" — the bottleneck was caught in usage metrics, not by eye. Told each VM's real memory apart from ZFS's ARC cache, avoiding false "RAM full" alarms.
  • Solved production failures: diagnosed via systemd logs the game daemon that wouldn't start behind the proxy, manually fixed its configuration and adjusted ports to operate behind Cloudflare.
  • 29 days of continuous uptime with 3 production VMs serving real institutional sites — including the university's community-service self-management platform.

Current status and roadmap

The server has considerable spare capacity —RAM, storage and a 48 GB GPU still unassigned— and the project is still being defined. Next steps include GPU passthrough for AI workloads, automated backups and new academic services according to the university's needs.

My role

Full server administration: hypervisor installation, disk recovery and conditioning, VM provisioning and tuning, no-public-IP network architecture, game hosting deployment, permission model and ongoing support for every VM's users — built and operated solo, on hardware nobody was using, over ~1 month of documented work.
